# DM 파일/이미지 첨부 — 둘만 볼 수 있는 첨부 만들기

**날짜**: 2026-07-28 · **티켓**: #184

## 무엇을 했나

1:1 쪽지(DM)에 파일과 이미지를 붙여 보낼 수 있게 했다.

- 보내는 사람은 **텍스트만 / 첨부만 / 둘 다** 아무거나 보낼 수 있다.
- 첨부 목록·다운로드는 **그 쪽지의 보낸 사람과 받는 사람만** 가능하다. 관리자도 못 본다.
- 이미지(jpg/png/gif/webp)는 대화창에 바로 보이고, 나머지 파일은 클릭하면 다운로드된다.

## 왜 필요했나

팀 과제나 계약을 이야기하다 이미지·문서를 보내려면 피드에 올리거나 메일을 써야 했다. 대화 흐름이 끊긴다.

그런데 DM 첨부는 **피드 업로드보다 더 조심해야 한다**. 피드 파일은 원래 모두가 보는 것이지만, DM 첨부는 둘만 봐야 하는 사적인 파일이다. 그래서 두 가지를 처음부터 못 박았다.

1. 파일을 **공개 경로(`/uploads`)에 절대 두지 않는다.** URL 만 알면 누구나 받을 수 있게 되기 때문이다.
2. **관리자 우회를 만들지 않는다.** 사업계획서 첨부(#125)는 채점 때문에 관리자가 볼 수 있지만, 사적인 대화는 그럴 이유가 없다.

## 어떻게 만들었나

### 1. 저장은 비공개 폴더에만

파일은 `PRIVATE_UPLOAD_PATH/dm/` 아래에 저장한다. 이 폴더는 웹서버가 정적 파일로 서빙하지 않는다. 즉 **URL 로는 도달할 방법 자체가 없고**, 오직 `GET /api/dm/attachments/:id` 를 거쳐야만 받을 수 있다. 그 API 가 "너 이 쪽지의 당사자 맞아?" 를 먼저 확인한다.

저장 파일명도 사용자가 올린 이름을 쓰지 않고 UUID + 확장자로 새로 만든다. 사용자 이름(`../../etc/passwd` 같은 것)이 그대로 경로가 되는 사고를 원천 차단한다.

### 2. 3중 검증 — 확장자, MIME, 실제 바이트

파일이 안전한지 확인하는 방법은 하나로 부족하다. 세 겹으로 봤다.

| 무엇을 보나 | 왜 |
|---|---|
| **확장자** | 허용 목록에 있는 것만 (`.jpg .png .pdf .docx .zip .mp4` 등). `.html` 은 아예 목록에 없다 |
| **MIME 타입** | 브라우저가 "이건 이미지야" 라고 알려준 값. 확장자와 어긋나면 거부 |
| **실제 첫 512바이트** | 파일 진짜 내용. PNG 는 `\x89PNG` 로, ZIP/docx 는 `PK` 로 시작한다 (매직 넘버) |

앞의 두 개는 **보내는 쪽이 마음대로 지어낼 수 있다.** `evil.html` 을 `photo.png` 로 이름만 바꿔 올릴 수 있으니까. 그래서 세 번째, 실제 바이트를 직접 읽는 검사가 진짜 방어선이다.

이 검사 코드는 새로 짜지 않고 기존 업로드 기능의 `validateUploadContent()` 를 그대로 재사용했다. 이미 검증된 코드를 다시 쓰는 게 새로 쓰는 것보다 안전하다.

`.html` 을 허용 목록에서 뺀 이유: HTML 안의 `<script>` 가 우리 사이트 출처에서 실행되면 남의 로그인 토큰을 훔칠 수 있다(저장형 XSS). #176 은 사업계획서 제출이라 꼭 필요해서 "다운로드 전용" 으로 조건부 허용했지만, DM 에는 그런 필요가 없다. **허용하지 않으면 막을 것도 없다.**

### 3. 다운로드 응답 헤더

| 종류 | 응답 |
|---|---|
| 검증된 이미지 | `Content-Type: image/png` + `inline` + `X-Content-Type-Options: nosniff` |
| 그 외 전부 | `application/octet-stream` + `attachment` + `nosniff` + `CSP: default-src 'none'; sandbox` |

`nosniff` 는 "내가 알려준 타입 그대로 믿어라, 내용 보고 멋대로 추측하지 마라" 라는 뜻이다. 이게 없으면 브라우저가 파일 내용을 훑어보고 "어 이거 HTML 같은데?" 하며 실행해버릴 수 있다.

중요한 점: **어떤 타입인지는 DB 의 `mime` 컬럼이 아니라 서버가 저장 파일명의 확장자로 직접 판단한다.** `mime` 은 업로드 당시 클라이언트가 보낸 값이라 신뢰할 수 없기 때문이다. 프론트엔드도 같은 기준(`stored_name` 확장자)으로 이미지/파일을 나눠서, 서버와 판단이 어긋나지 않게 했다.

### 4. 고아 파일이 남지 않게

파일은 디스크에 쓰고, 기록은 DB 에 남는다. 둘 중 하나만 성공하면 **짝 잃은 쓰레기**가 생긴다.

- 디스크에는 있는데 DB 에 없다 → 아무도 못 지우는 유령 파일
- DB 에는 있는데 디스크에 없다 → 클릭하면 깨지는 첨부

그래서 이렇게 했다.

- 여러 파일 중 **하나라도** 검증에 실패하면, 그 전에 이미 쓴 파일까지 전부 지운다.
- 쪽지 행과 첨부 행은 **하나의 트랜잭션**으로 함께 넣는다. 중간에 실패하면 통째로 취소되고, 디스크 파일도 정리한다.

### 5. 개수·크기 한도

파일당 **10MB**, 메시지당 **최대 4개**, 합계 **20MB**.

숫자를 이렇게 잡은 이유가 있다. 앞단 nginx 가 요청 하나를 50MB 까지만 받는다. 만약 "10MB × 5개 = 50MB" 로 잡으면 테스트는 통과하는데 **실제 서비스에서만 413 에러**가 난다. 테스트 환경에는 nginx 가 없으니까. 한도는 항상 제일 좁은 관문에 맞춘다.

### 6. 알림

첨부만 보낸 쪽지는 본문이 비어 있다. 알림에 빈 줄이 뜨면 이상하니까, 전부 이미지면 "사진을 보냈습니다", 아니면 "파일 N개를 보냈습니다" 로 대신 보여준다.

## TDD 로 만들기

먼저 **실패하는 테스트 15개**를 쓰고 시작했다. 통합 테스트가 검사하는 것:

- 제3자와 **관리자**가 받으려 하면 403
- 위조된 PNG(`evil.png` 안에 `<script>`), 금지 확장자(`.html`, `.exe`), MIME 불일치 → 400
- 용량 초과, 개수 초과 → 400 **그리고 디스크에 파일이 남지 않음**
- 위험한 파일명(`../../etc/passwd`, 따옴표·개행 포함) → 거부
- 텍스트만 / 첨부만 / 둘 다 모두 전송 성공, 다시 조회해도 첨부가 살아있음
- 다운로드 응답 헤더가 정확함

프론트엔드 vitest 10개는 첨부 선택 → 미리보기 칩 → 제거 → FormData 전송, 그리고 이미지 inline 렌더 / PDF 다운로드 버튼을 검사한다.

## 배운 점

**"관리자는 다 볼 수 있다" 가 기본값이 아니다.** 사업계획서(#125)는 채점해야 하니 관리자 접근이 맞고, 사적인 쪽지는 아니다. 같은 "비공개 첨부" 라도 목적에 따라 권한 규칙이 달라진다. 코드를 복사할 때 권한 검사까지 같이 복사하면 조용히 구멍이 뚫린다.

**막을 방법을 고민하기 전에, 허용하지 않는 게 먼저다.** HTML 을 안전하게 처리하는 방법을 궁리하는 것보다, 목록에서 빼서 **실행될 경로 자체를 없애는** 편이 훨씬 확실하고 코드도 짧다.

**한도는 제일 좁은 관문에 맞춘다.** 테스트만 보고 정한 숫자는 프로덕션에서 터진다.
